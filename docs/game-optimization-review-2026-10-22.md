# new-api 游戏中心优化审查（2026-10-22）

范围：当前工作区 28 款游戏的前端入口、共用交互、对应 controller、规则引擎及相关模型。目标是寻找仍有价值的正确性、恢复、性能与易用性改进。本轮只审查和验证，没有修改业务代码或运行配置。

证据等级：**复现**表示通过实际源码片段执行验证；**静态确认**表示读通了触发条件和调用链；**可选**表示已有明确实现依据，但需要按产品需求或性能测量决定是否实施。下面的 P2 是应安排修复的普通缺陷，P3 是低影响文案、体验或性能优化；未作完整浏览器、数据库并发或线上验证，不据此宣称没有其他问题。

## 优先处理的问题

### O01：象棋提示收费后，响应丢失不能找回分析（P2，隔离接口复现）

人机提示先通过 `ChargeGameSessionState` 提交次数、费用和新版本，再返回分析。象棋存档只增加 `Hints`，分析内容没有持久化。响应丢失后，前端 GET 恢复接口只能拿回局面、次数和下一次费用，不能拿回已付费的提示；刷新页面同样会丢失提示。再次点击会使用恢复后的新版本再次消耗次数，免费额度用完时再次收费。

- 位置：`controller/game_pvp.go:1982`、`:2047`、`:1611`；`controller/game_xiangqi.go:680`、`:692`；`web/classic/src/pages/Games/common/pvp/PvpGame.jsx:1035`、`:1198`。
- 建议：以对局和局面标识关联最后一次分析，在扣费事务中保存结果，恢复接口返回已生成的分析。重复读取同一份提示不再收费；走棋、悔棋、换局后按局面标识失效。
- 验收：第四次提示提交扣费后模拟响应丢失，恢复或刷新应能看到原提示；不得为找回同一提示再次扣币。请求在提交前取消仍应维持已有的不收费行为。

### O02：连连看倒计时提前发送主动放弃（P2，源码片段复现）

前端 `accept` 使用 `elapsed + 1` 推算起始时间，随后倒计时归零自动调用 `finish`。例如服务端返回 `elapsed=179, seconds=180, status=playing`，前端立即算出剩余 0 秒。服务端实际超时条件是 `elapsed > seconds`，但 `action=finish` 不论当前是否超时都会判负。因此客户端把仍可合法操作的一局提前结束了。

- 位置：`web/classic/src/pages/Games/pairlink/index.jsx:68`、`:175`；`controller/game_pairlink.go:101`。
- 建议：自然超时由服务端确认；倒计时归零触发核实超时的操作，保留 `finish` 给主动放弃。返回绝对截止时间和服务器当前时间，消除人工减一秒的偏差。
- 验收：覆盖 `elapsed=179/180/181` 的 180 秒局；前两种不能仅因前端倒计时而主动判负，真正超时后仍必须结束。

### O03：扫雷、数独、华容道存储异常中断页面（P2，源码片段复现）

三款游戏的恢复读取有保护，但保存进度的 effect 直接调用 `localStorage.setItem`，没有捕获存储配额或访问策略异常。抛出的异常会进入应用错误边界。开局和结束时还有未保护的 `removeItem`，存储访问失败可能中断恢复步骤。推箱子已有同类写入的异常保护，不能把它列为同一问题。

- 位置：`web/classic/src/pages/Games/minesweeper/index.jsx:158`、`:209`；`sudoku/index.jsx:164`、`:240`；`puzzle15/index.jsx:175`、`:239`。对照：`sokoban/index.jsx:103`。
- 建议：保存或清理失败不打断当前对局；降级为当前页面内存保存，并提示刷新恢复可能不可用。避免每一步重复弹错误。
- 验收：模拟 `QuotaExceededError` 和 `SecurityError`，三款均能继续操作、结算，已有内存进度保留。

### O04：2048、贪吃蛇双指触摸吞掉滑动（P2，源码片段复现）

第二个 `pointerdown` 会覆盖第一个指针记录；任何 `pointerup` 都先清空记录，再检查指针 ID。按顺序执行指针 1 按下、指针 2 按下、指针 1 松开、指针 2 松开，两次滑动都没有被处理。普通单指同样的位移能正常生成向右操作。

- 位置：`web/classic/src/pages/Games/g2048/index.jsx:305`、`:315`；`snake/index.jsx:468`、`:478`。
- 建议：保留一个活动指针，忽略无关的按下/抬起事件；仅在匹配的指针结束、取消或失去捕获时清理。不能简单禁止整个游戏的所有多指操作，俄罗斯方块等多按钮操作有不同需求。
- 验收：两指交错按下/抬起仍保留主指针操作；取消、离开和下一次单指滑动不会沿用旧坐标。

### O05：Plinko 恢复请求和旧动画能覆盖较新显示（P2，静态确认）

投球请求失败后先释放请求锁，再异步调用 `loadInfo(true)`；重载没有代次保护。旧重载晚于后续成功投球返回时，可以覆盖较新的 `balance`。另外，重载已经取得最新账户信息后，仍在飞行的旧球落地会用该球的旧快照写回 `shownBalance`、今日输赢与次数。后端实际账本不受这些前端覆盖影响，但按钮判断或显示可能回退。

- 位置：`web/classic/src/pages/Games/plinko/index.jsx:237`、`:255`、`:286`、`:357`。
- 建议：将恢复纳入操作锁，或使用请求代次丢弃过期响应；将权威账户快照与动画揭晓状态分离，旧球可以展示自身结果，但不能覆盖更新的账户快照。
- 验收：延迟一次恢复 GET，使其晚于下一次投球返回；再让较早的球落地，账户信息仍保持最新值。

### O06：奖池旧轮询响应能覆盖投入后的新状态（P2，静态确认）

奖池每 2 秒轮询，轮询与投入都直接调用 `apply`，没有共享的请求代次或状态版本判定。投入前发出的 GET 如果晚于成功投入的 POST 返回，会把余额、个人投入、奖池金额等覆盖成投入前的值。慢请求之间也可能乱序；下一次刷新可纠正，但期间页面会显示过时状态。

- 位置：`web/classic/src/pages/Games/jackpot/index.jsx:114`、`:149`、`:181`；`common/useVisiblePolling.js:25`。
- 建议：单个轮询在途时不再重复发起；投入时使此前的轮询代次失效，投入完成后再恢复轮询。仅暂停新定时器不够，还要拒绝旧在途响应。服务器时间当前只到秒，也不宜单独拿它作版本号。
- 验收：控制 GET/POST 响应顺序，旧 GET 不得回退已成功投入后的 `mine/pot/balance` 或已结束轮次。

### O07：21 点“必须偶数下注”说明过时（P3，静态确认）

规则说明仍写黑杰克赔 3:2，因此下注必须是偶数。当前请求使用 `GameCoins`，服务端 `validWagerBet` 接受合法范围内、最多两位小数的下注，并不存在该偶数限制。

- 位置：`web/classic/src/pages/Games/blackjack/index.jsx:224`；`controller/game_blackjack.go:147`；`controller/game_wager.go:58`。
- 建议：删除偶数限制说明，准确区分返还本金与净赢倍率，并同步对应翻译。无需为匹配旧文案而恢复后端偶数限制。
- 验收：说明与 1 币、0.01 币等合法下注及实际派彩规则一致。

### O08：奖池晚到的投入可能被扣入下一轮（P2，隔离接口复现，优先处理）

投入请求只有 `amount`，没有用户看到的 `round_id`。控制器先处理到期奖池，再调用模型投入；模型没有开放轮时自动创建下一轮。因此玩家在 A 轮倒计时结束前点击，服务端稍晚收到时可能先开奖 A，再把钱扣入 B。模型确实检查锁定轮次是否过期，但无法保护请求中根本没有传来的预期 A 轮。这是投入目标与操作意图不一致，并非发现了重复扣款或派彩溢出。

- 位置：`web/classic/src/pages/Games/jackpot/index.jsx:185`；`controller/game_jackpot.go:197,220`；`model/game_jackpot.go:76,105`。
- 建议：请求携带预期轮次，在扣币事务内核对；轮次改变时返回明确的过期响应，刷新后由玩家决定是否投入新轮。尚无开放轮时的首次投入语义也要明确。
- 验收：创建两人参与的 A 轮，模拟用户读取后 A 到期，再发送原投入。修复后应拒绝且不扣币，不应自动创建或加入 B。

### O09：大转盘跨日不刷新免费次数（P2，静态确认）

免费选择仅依据当前内存的账号/IP 已用次数。信息在挂载或错误恢复时读取，付费响应不带免费次数并保留旧值。昨天用完免费次数后页面跨过服务端记账日，今天点击仍发送 `free:false` 并付费，新一天的免费机会没有刷新。按钮也显示付费，因此不能描述为“显示免费却扣费”。

- 位置：`web/classic/src/pages/Games/wheel/index.jsx:198,231,248,293`。
- 建议：由服务端返回记账日或下次日切时间；跨日与重新可见时刷新规则和次数，再决定免费/付费模式。保留免费请求失败不自动改成付费的现有行为。
- 验收：账号和 IP 昨日次数用完，页面保持打开跨日，今日首次操作应显示并选择今日免费额度；按服务器时区验证，不能假定浏览器午夜就是日切。

### O10：老虎机、轮盘前端没有开放后端支持的小额下注（P3，功能一致性）

后端统一支持 0.01 币、最多两位小数；老虎机的可操作判断要求 `bet >= 1` 且只提供整数加减，轮盘筹码从 1 开始且要求 `total >= 1`。例如余额 0.50 时，用户无法从这两个页面使用服务端支持的小额下注。

- 位置：`web/classic/src/pages/Games/slots/index.jsx:328,464`；`roulette/index.jsx:36,100`；`controller/game_wager.go:26,58`。
- 建议：统一最小下注规则；老虎机可复用 `BetInput`，轮盘可增加小额或自定义筹码，并按分计算筹码合计。若有意维持不同的前端产品门槛，则应明确说明，不能把它误认为后端限制。

### O11：高低牌封顶前的下一步倍率与派彩不匹配（P3，展示准确性）

接口将下一步未封顶的累计倍率和已经按 1000 倍封顶的派彩并列返回，前端直接显示 `×multiplier · payout`。接近上限时可能显示超过 1000 倍的倍率，旁边金额却只按 1000 倍计算；规则说明已有封顶，金额不会因此超额派发。

- 位置：`controller/game_hilo.go:101`；`web/classic/src/pages/Games/hilo/index.jsx:242`；`pkg/hilo/hilo.go:110`。
- 建议：显示实际有效倍率，或明确标注“理论倍率 / 已封顶派彩”。验收覆盖下一步跨过 1000 倍的状态。

## 跨游戏的改进与边界

1. **待结算录像持久化（P2，恢复完善）**：方块、2048、贪吃蛇、像素鸟、打砖块虽有内存重试，其中四款还有离页时尽力提交，但刷新/关闭浏览器不能依赖普通异步请求。可按用户、对局、录像格式版本保存待提交记录，收到服务端确定结果后再清理；保留服务端重放、会话归属与过期校验。先处理未知结算的恢复，不必一开始实现完整跨设备续玩。
2. **一次性下注结果恢复（P3，新增能力）**：老虎机、转盘、Plinko、骰子、轮盘、刮刮乐可逐步统一请求标识与结果查询。不能把当前的账户重读说成没有恢复能力，也不能将一次新下注当成原请求的安全重试。这需要服务端协议及事务幂等设计，不只是前端加一个按钮。
3. **PvP 倒计时与棋盘分离（P3，待测量）**：`RoomView` 每 500 ms 更新 `now`，重新调用 `renderBoard`。可把计时与可操作状态局部更新，必要时稳定 props 后增加 memo 边界；不机械地给所有组件加 memo。已确认重复渲染路径，但未测得帧率或耗电改善值。
4. **AI 取消（P3）**：共用框架支持 `AiMoveContext`，象棋已实现；五子棋、四子棋、黑白棋仍只实现同步 `AiMove`。请求取消后框架会丢弃结果，但搜索仍占用名额直到结束。现有节点预算有界，建议加取消检查，而不是把它描述成无限计算。
5. **操作反馈优先于冒进的乐观展示**：扫雷、记忆翻牌、高低牌等有隐藏信息，弱网优化应排队意图或显示在途操作，不能让客户端预先拿到隐藏状态。资金操作仍由服务端决定结果。
6. **保持经济规则**：本轮没有提出提高奖励、改变 RTP、放松限额或取消防重放措施的建议。优化恢复/渲染不应改变这些规则。
