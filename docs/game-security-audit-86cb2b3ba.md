# new-api 游戏中心逐项安全审查

审查基线：`86cb2b3ba`，2026-10-13。覆盖已注册的 28 个玩法、对应规则引擎与控制器，以及共享会话、奖励、钱包、房间鉴权、状态恢复和扫尾路径。

基线结论：确认 1 类 P2 问题，影响连连看及 5 个游戏的人机模式；其余 22 个玩法在本次审查范围内未发现可证实的漏洞。未发现可复现的无限派奖、越权读取他人暗牌或下注套利路径。“未发现”不等于不存在漏洞，现有测试通过也不代表完成了全部安全证明。

后续修复：GC-01 已在本报告随附的修复中处理。连连看放弃或超时、人机认输只使用此前有效操作已保存的 `PlaySeconds`；连连看零消除时计 0 秒，AI 开局自动走棋也不计玩家时长。正常最后一步仍使用 `PlayedSeconds`，保留真实游玩补领待发奖励。下面的复现和覆盖表描述的是审查基线，不代表修复后的现状。

## GC-01 / P2：零操作挂机可补足待发奖励的游玩时长

涉及连连看，以及五子棋、四子棋、黑白棋、中国象棋和斗地主的人机模式；这五个游戏的玩家对战模式不受此问题影响。

- [连连看结算](../controller/game_pairlink.go#L153) 对主动放弃或超时的对局仍直接累计 `session.PlayedSeconds(...)`，即使没有消除任何一对。
- [人机结算](../controller/game_pvp.go#L1474) 同样无条件累计该时间，而 [认输入口](../controller/game_pvp.go#L1561) 不要求玩家走过任何一步。
- [时长计算](../model/game_session.go#L97) 把未操作对局从开局到结束的等待也计入，单次最多 60 秒。共享结算允许本局得分为 0 时释放之前已经取得的 `PendingReward`，因此等待可以充当补领奖所需的实际游戏时长。

前置条件是用户已经正常达标并取得待发奖励。此问题不绕过成绩要求、每日领奖次数、IP 次数或奖励总上限，也不能凭空从无待发奖励的账户领取游戏币。

已验证的复现：

1. 连连看保留默认奖励规则，仅打开游戏。难度 2 在 5 秒内按合法路径消除 24 对，得到 1 币待发奖励，尚未满足每币 120 秒。
2. 再开两局，每局不消除任何一对，等待 61 秒后直接 `finish`。两局均返回 `pairs=0、score=0`，但各累计 60 秒。
3. 当天累计时间达到至少 125 秒，1 币实际入账。

五个人机模式分别经 HTTP 开局和零步认输验证，隔离测试将每币时长设为 60 秒，并先通过真实结算函数生成 1 币待发奖励；每个模式均出现 `score=0、reward=1`，余额从 0 增至 1。默认规则下，在已有 1 币待发且累计时长为 0 的情况下，所需零步挂机次数如下；已有有效累计时长时会更少。

| 模式 | 默认每币时长 | 每次挂机 60 秒所需次数 |
| --- | ---: | ---: |
| 五子棋人机 | 180 秒 | 3 |
| 四子棋人机 | 120 秒 | 2 |
| 黑白棋人机 | 180 秒 | 3 |
| 中国象棋人机 | 300 秒 | 5 |
| 斗地主人机 | 180 秒 | 3 |

测试仅在独立数据库中调整时间字段来模拟时间经过，没有真实等待或修改生产数据。实际用户仍需经过相应的墙钟时间。

建议让有效玩家操作成为计时依据：零操作放弃、超时或认输应贡献 0 秒；区分玩家操作与开局自动执行的 AI 操作。保留“有效游玩补足之前待发奖励”的行为，并补充上述六个模式的回归。
