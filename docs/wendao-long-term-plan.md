# 问道后续开发长期方案与交接书

编制日期：2026-11-01。代码基线：`dcaf1997dc8e142066c69c686e0bd0bc6d217e9d`。

本文供后续开发者、策划和验收人员共同使用。它记录当前已经实现的功能、后续开发顺序、可以分派的工作包和完成标准。**建议先用六个月完善现有玩法的体验、成长节奏和持续内容，再根据实际玩家数据决定第七至十二个月的大版本。**

2026-11-02 起已按本文在功能分支 `feat/wendao-next` 上开发了 A2（部分）、A3（测量）、B1、C2、C3；2026-11-03 在 `feat/wendao-content` 上开发了 A4、C4、C5 与 B3 的派遣一键结算。各工作包下面的「进度」写明了交付内容与未覆盖项；其余工作包仍是待开发内容。

本次核对依据是仓库代码、设计文档和本地测试。没有读取生产存档、线上运营数据，也没有在本轮完成浏览器全流程验收。文中的排期、体验目标和立项门槛均为建议；“当前状态”才表示已经从代码确认的事实。本文列出的新工具、新接口、新表及新功能均是后续交付项，不表示已经开发。

## 1. 开发目标和执行约定

问道的定位保持为“主角历练、宗门经营、九幽秘境互相支撑的长线修仙游戏”。未来半年优先做到四件事：

1. 新玩家第一次进入时，能理解自己是谁、当前可以做什么，以及资源从哪里来。
2. 老玩家每次回来都有明确的短期目标，同时能看到一周和一个月后的成长方向。
3. 卡牌、弟子、洞府、炼丹、炼器和灵兽形成可选择的养成路线，能够解释胜负和资源取舍。
4. 更新内容时保住旧进度、进行中的战斗、交易和奖励，不依赖开发者本机上的临时工具。

后续开发沿用以下边界：

- 永久进度不因普通版本更新、周挑战换期或论剑赛季切换而清空。
- 宗门资源、丹药、灵药与游戏币分开。新加支线、周挑战、图鉴和养成奖励默认只发游戏内资源或展示奖励。
- 涉及游戏币的变更，必须单独写清奖励预算、成绩口径、有效时长和重复结算处理。本文不授权提高线上发币额度。
- 前端只在 `web/classic/` 开发，文案接入现有七种语言的 i18n；继续使用现有 SVG、美术变量和减少动态效果约定。
- 后端继续由规则包负责玩法、控制器负责鉴权和编排、模型层负责事务。数据库同时支持 SQLite、MySQL 和 PostgreSQL。
- 不以一次性重写为前置条件。按下面的工作包逐步交付，每个工作包都能独立检查并说明兼容办法。

| 灵兽 | 六种、引兽与孵化、资质、喂养、亲密、进化、出战与放生 | 先测各灵兽的实际价值，再扩展品种和技能 |
| 九幽秘境 | 无尽、试炼、练习；三流派、道韵天赋、卡牌肉鸽战斗 | 扩构筑和遭遇变化，保持与主角养成的边界 |

因此，下一阶段的重点是完善现有系统之间的关系和持续内容。洞府、炼丹、炼器、灵兽、仙盟、交易所都不需要再作为“从零建设”的项目报价。

### 2.2 奖励和养成边界

| 内容 | 当前奖励/消耗 | 开发时需要守住的边界 |
| --- | --- | --- |
| 秘境无尽 | 可以发游戏币，标识 `wendao`；也有道韵与有限次数的宗门材料 | 不带入主角境界、收藏牌组、洞府、祭炼、灵兽等主角养成；秘境自己的道韵天赋仍生效 |
| 宗门大比 | 可以发游戏币，标识 `wendao_tournament`；另有宗门资源 | 仍使用真实弟子与库存丹药，对手按实力自适应；不能宣传为完全等属性 |
| 历练、问心阶、洞府 | 修为、卡牌、法宝、材料及主角成长 | 不因新增奖励入口绕到游戏币结算 |
| 论剑、仙盟、灵田、功课、万宝阁 | 宗门资源、丹药、灵药、积分等 | 不新增可反向兑换游戏币的资产 |
| 宗门商店丹药 | 消耗游戏币，进入与自炼丹药相同的库存 | 当前万宝阁可流通这些丹药，核对时应包含这条间接资源流转路径 |
| 宗门符箓、秘境商店道具 | 消耗游戏币，持有后在对应玩法使用 | 保留现有扣费、持有与使用限制，不作为万宝阁货物 |

需要特别说明：`world.md` 的公平原则需要结合实际模式理解。秘境允许自身道韵成长和现有商店道具；大比也保留了弟子差异及库存丹药，通过对手强度公式缓和差距。**“已有自适应”不等于“已证明所有养成路线具有相同领奖概率”。**第一阶段应补数据验证，现有大比规则的重大调整另行设计，不能夹在普通养成更新里改掉。

配置中的默认值不代表线上实际配置。当前代码默认秘境无尽为每天一次、达到一重、每币累计有效游玩 300 秒；大比为每天一次、连胜三场、每币 180 秒，默认奖励均为一币。管理员可以调整它们。后续验收应导出当时的脱敏配置，而不是把本段当成固定产品承诺。

### 3.2 接口和存储关系

所有下列相对路径均位于 `/api/game/wendao` 下，需沿用现有登录、限流和开关检查。

| 接口 | 用途 |
| --- | --- |
| `GET /api/game/wendao` | 三板块规则、公共信息与领奖进度 |
| `GET /hero`、`POST /hero/action` | 主角状态与历练、洞府相关操作 |
| `GET /abyss/state`、`POST /abyss/start`、`POST /abyss/action` | 秘境恢复、开局、行动；另有解锁与商店 |
| `POST /sect/action` | 宗门经营与同步；注意不是 `GET /sect` |
| `/sect/tournament/*`、`/sect/arena/*` | 大比与论剑恢复、开局、行动、守擂 |
| `/sect/alliance/*` | 仙盟相关操作 |
| `/sect/garden/neighbors`、`/sect/garden/visit` | 道友列表、拜访、浇灌和摘取 |
| `/sect/market`、`/list`、`/buy`、`/cancel` | 万宝阁查询、挂单、成交和撤单；后三者接在 `/sect/market` 后 |

长期进度放在 `GameSave`，主键为玩家与游戏标识，问道统一使用 `wendao`。其中 `Sect`、`Hero`、`Abyss` 分别是宗门、主角和秘境局外进度。**主角正在打的单场战斗也在 `Hero.Battle` 中，因此长期存档的容量评估必须包括战斗状态。**

秘境单局、大比和论剑使用现有对局体系；秘境试炼、练习还有 `wendao_trial`、`wendao_practice` 对局标识。不要把它们误当成新的长期存档。秘境当前一局有效期是七天，更新时还要处理仍在进行的旧局。

普通存档改写经过 `UpdateGameSave`；串门等双人改写经过 `UpdateTwoGameSaves`，按玩家编号顺序锁存档。万宝阁成交先锁挂单，再按编号锁两份存档，并在同一事务中完成货物、灵石、税和挂单状态变化。新功能必须沿用这些事务关系。

## 5. 六至十二个月路线图

排期假设：一名 Go 开发、一名 React 开发，另有兼职测试与策划。人日为前后端开发合计估算，未含美术、翻译和额外专项测试；排计划时再预留约 25%–30% 的验证、修复与联调时间。实际开始日期由接手团队填写，不将这些区间解释为已经承诺的上线时间。

| 阶段 | 建议时间 | 开发量 | 本阶段交付 | 进入下一阶段的条件 |
| --- | --- | --- | --- | --- |
| A：可交接、可升级 | 第 1–2 周 | 11–18 人日 | 入库工具、存档迁移与容量报告、奖励核对 | 新环境能复现；兼容和发币边界检查通过 |
| B：第一次玩与每天回来 | 第 3–6 周 | 18–29 人日 | 目标提示、引导、批量操作、战斗操作、弱网恢复 | 完成新手和回流验收，重复请求不重复扣发 |
| C：构筑和可重复内容 | 第 7–12 周 | 24–39 人日 | 平衡报告、牌组预设、周挑战、两段支线、成长反馈 | 新内容不破坏永久进度和游戏币边界，有至少两轮周内容验证 |
| D：社交与持续运营 | 第 4–6 月 | 19–30 人日 | 仙盟机制轮换、条件性论剑赛季、内容发布流程、只读诊断 | 活跃供给满足所选玩法；换期、领奖和配置可追踪 |
| E：大版本储备 | 第 7–12 月 | 35–60 人日，需重估 | 新地域/新境界完整设计与实现，或继续补现有终局 | A–D 稳定；明确选择一个大版本方向后再排产 |

依赖关系：A2、A3 在引入更多永久字段前完成；A1、A4 是平衡与新剧情的工具前置；A5 是新增任何奖励入口的前置；B5 是批量操作、周领奖和赛季结算的公共前置；C1 的结果决定 C3 难度和 E 的成长空间。

只有一名全栈开发时，按 A → B → C 顺序交付，六个月先保证这三阶段；D、E 顺延。人手减少时优先缩减新内容数量，保留存档、结算和恢复验收。

## 6. 可直接分派的开发工作包

每个编号应成为独立任务或小型 PR。接手者补负责人、开始日期、实际工时和验收链接；不要把整份方案合成一个大 PR。

### A：基础与交接

**A1｜把平衡和升级工具变成可复现交付物｜2–3 人日｜后端主责**

- 输入：附录中的本机临时工具、现有规则包和本文件的基线。
- 交付：仓库内的工具入口、运行说明、固定样本/种子、依赖版本、输出示例和明确的测试库配置。建议目录为 `scripts/wendao/`、`scripts/upgrade/`，最终遵循仓库实际组织。
- 先审查临时脚本，去掉写死盘符、用户名、二进制路径、个人凭据和旧端口。升级脚本必须只操作显式指定的可丢弃库；无参数时不得尝试连接默认业务库。
- 验收：另一台机器从仓库和文档能复现同一份规则基线报告；不要求把开发时用过的改文件脚本全部保留。模拟报告不能代替行为断言或真人体验。

**A2｜补存档 schema 与迁移契约｜3–5 人日｜后端主责**

- 交付：根存档版本设计、旧样本、逐版本迁移、未来版本拒绝写入、错误定位办法及一次往返读写验证。
- 区分三种版本：数据库行的并发写入计数、长期存档的 schema、进行中对局的规则/状态格式。不要用同一个数同时承担三种职责。
- 旧存档缺字段应补业务默认值，不能赠送重复首通奖励、重置功课或重复结算离线产出。对损坏数据报告可诊断错误，不静默创建新存档覆盖。
- 验收样本覆盖：空存档、只有宗门、无洞府的老主角、进行中的历练/秘境/大比、已种灵田、未完成丹炉、孵化中灵兽、满收藏和终局进度。迁移两次等于一次，读后写再读不丢资产与进度。
- 进度（2026-11-02）：根存档已加格式版本 `schema`（`wendao.SaveSchema`，当前为 1，写存档时记上）。读到比程序新的存档时返回 `ErrNewerSave`，读写接口都拒绝并提示请管理员升级，存档原样不动（`TestNewerSaveIsRefused`、`TestNewerWendaoSaveIsNotOverwritten`）。v2.16.23 及以前的程序不认识这个字段，保护从下一次加一开始生效；以后往存档里加旧程序不认识的字段时要把 `SaveSchema` 加一，并在 `ParseSave` 写迁移。逐版本旧样本与进行中对局的格式版本还没有做。

**A3｜量化容量并验证三库升级｜2–4 人日｜后端主责**

- 分别测量共用存档和各类对局状态的 UTF-8 字节数，包括满收藏、最多弟子、日志、丹炉、灵兽和进行中的战斗；在每个关键样本记录字段贡献。
- 核对新建库与升级库的真实列定义。若继续使用 MySQL 普通 TEXT，建议最大受支持样本留到不超过 48 KiB 的余量；该数字是工程目标，不是当前实现的已有上限。
- 若合法状态可能逼近或超过 65,535 字节，按数据库方言扩容：MySQL 使用合适的大文本类型，PostgreSQL/SQLite 保持有效文本类型；新建库、老库和重复启动均需验证。不能靠截断 JSON、删除卡牌、清战斗或压缩玩家进度来凑容量。
- 验收：三种数据库分别完成新建、旧版升级、再次启动、读写大样本、事务失败回滚。报告列出执行环境；仅在 MySQL 8 跑过不能宣称已覆盖项目要求的 MySQL 5.7.8 最低版本。
- 测量（2026-11-02，单元测试里拼样本，未入库）：12 名满境界弟子、4 支派遣、30 条大事记、80 张参悟过的功法、30 张牌组、55 个节点全通、问心阶开战中带两名随行弟子的存档约 14.6 KB，其中进行中的战斗约 3.5 KB；秘境一局（70 张牌、20 件法宝、无战斗）约 4 KB。距 MySQL `TEXT` 的 65,535 字节约有四倍余量，本轮不改列类型。三库真实列定义与 MySQL 5.7 还没有核对。

### B：新手、日常操作与恢复

**B1｜主目标与跨板块待办｜3–5 人日｜前端主责**

- 在现有外壳或概览中展示一个主目标、最多三项可操作待办和一个明确入口。例如“突破筑基还缺修为/机缘”“有一炉丹可收”“有一支派遣可领”。
- 展示缺口、来源、预计等待和可采取的操作。服务器负责真实可操作条件与时间，前端倒计时只作显示；没有准确数据时不伪造剩余时间。
- 优先使用现有响应，确有缺口再补摘要字段。跨板块操作后刷新相关资源和目标，不要求玩家重新进入整个游戏。
- 验收：新账号、卡境界、没有成熟作物、离线超过十二小时、第五章通关等状态都有合理目标；点击后能到正确板块，且没有用提示代替服务器校验。
- 进度（2026-11-02）：已交付第一版。规则在 `pkg/wendao/agenda.go`，只读接口 `GET /api/game/wendao/agenda`，三个板块顶上共用 `Games/wendao/Agenda.jsx`：一个主目标（下一个主线节点、修到圆满、带机缘突破、登问心阶、登顶）和按急迫程度排的待办，点了跳到对应板块、页签、洞府分区或地图节点，别的板块的待办件数标在板块按钮上。测试 `TestAgendaGoalFollowsTheJourney`、`TestAgendaTodosListWhatCanBeDoneNow`、`TestWendaoAgendaThroughTheApi`；浏览器里看过浅色、深色和 390px 宽。离线超过十二小时的回流说明属于 B2，还没做。

**B2｜首轮引导与回流说明｜3–5 人日｜前端主责，策划提供文案**

- 用实际玩法串起创建主角、一次战斗、宗门资源、一项经营和下一次成长；分次解释道韵、灵珠、灵石、游戏币。
- 引导可跳过、可回看，刷新后不从头强迫重做。使用正常首通/经营流程，不发会被反复触发的新手奖励。
- 回流时说明离线收益上限、已完成事项和未完成目标。暂时不能社交或交易时，解释条件，不把玩家卡在必须等待其他人的引导步骤。
- 验收：找未参与开发的人走首轮，记录在哪里停住和误解术语；建议五位体验者中至少四位不靠口头提示完成首个循环。该目标属于验收建议，当前未进行这项测量。

**B3｜安全的批量操作与计时反馈｜4–6 人日｜前后端协作**

- 首批只做“收获所有已成熟作物”和“领取所有已完成派遣”，以后再根据点击量补其他操作。
- 单次请求内按当前服务器状态确定可领取对象并完成事务，未成熟项目跳过；返回逐项结果和合计，资源、功课进度与日志沿用单项业务规则。
- 给丹炉调火、孵化、丹药冷却、派遣和受伤显示明确状态。支持错过调火仍可正常收丹，不把几小时定时回访变为必须完成的任务。
- 验收：没有可领项目时安全返回；连点、并发、响应丢失后重试均不会重复给奖励；某个对象已经被领过时不会把其奖励再算到合计里。
- 进度（2026-11-03）：「收获所有已成熟作物」之前已有（`harvest_all`），这次补上「领取所有已完成派遣」：宗门操作 `claim_all` 按出发先后逐支结算已经回来的派遣，每支的成败、收获、掉落与受伤和单独结算一样；一支都没回来时返回不可用，结算过的派遣已从存档里拿掉，重复请求不会再领一份（存档改写沿用原有的加锁与版本检查）。每日功课「领取派遣收获」按这次结算了几支记。派遣页有两支以上回来时标题旁出现「全部结算（N）」；宗门页的结果提示逐条写每支的成败，资源、灵药与丹药按种类合计成一笔（一键收获也一样）。历练页主角卡在聚气丹冷却时直接写出还要多久，不再只藏在按钮的提示里。测试 `TestClaimAllReturnedMissions`。丹炉调火、孵化、受伤与派遣的倒计时原本就写在各自的卡片上，这次没动。

**B4｜战斗可读性与操作｜3–5 人日｜前端主责**

- 强化敌人已公开意图、目标选择、状态层数与持续回合、丹符消耗和灵兽行动反馈；对失败指出可理解的原因与可尝试的成长方向。
- 为桌面增加可查看和可关闭的快捷键。输入框、弹窗、选择奖励、请求中和非当前战斗时不响应；结束回合等关键动作避免误触。
- 手机保持点击即可完成全部操作，支持 320/375/430px 宽度、横屏与键盘焦点；动画和音效服从现有偏好。
- 伤害预览只展示规则可以确定的部分，不消耗随机数或提前显示未公开结果。预览正确性无法保证的机制明确标范围或暂不预览。
- 验收：历练与秘境共用战斗组件时行为一致，新增展示不改变伤害、回合和敌人出招；不开声音和关闭动画也能看清结果。

**B5｜弱网、多端和请求重复处理｜5–8 人日｜前后端协作**

- 优先为稀有材料消耗、商店购买、关键领取补业务幂等收据。现有对局 CAS、挂单状态检查与业务幂等各有作用，不能互相替代；同一请求标识携带不同内容应拒绝。
- 需跨节点保证的幂等放在数据库唯一约束/事务中，不依赖单进程内存。前端禁用按钮仅用于交互反馈。
- 验收：模拟“服务端已提交、客户端未收到”的中断；再次操作能恢复结果，不重复扣料、祭炼、购买或发奖。两个标签页同时出牌、收获、买同一挂单时，只有合法状态被保存。

### C：构筑、平衡和持续内容

**C1｜完整成长和平衡报告｜6–10 人日｜后端与策划主责**

- 覆盖三流派、章节首领、问心阶、洞府、祭炼、丹药、随行弟子和六种灵兽。至少比较基础角色、同阶段合理培养、毕业培养三类状态。
- 模拟工具输出固定样本的胜率、回合数、失败原因、突破耗时、资源缺口和各养成投入收益；对随机结果说明样本数与不确定性。
- 在 7/30/90 天的合理上线频率下算资源收支，区分零商店消费、使用现有道具和活跃玩法收入。重复刷取、指名赠送与丹药加速也进入模型。
- 同一调整中记录调前/调后，不同时大改经验、敌人、材料与奖励后只看总通关率。机器人适合查数值趋势，不能证明真人理解构筑或喜欢节奏。
- 验收：策划给出每境目标时间、难点与可选路线；三流派均有可完成主线和终局的方案。增加灵兽等养成后重新评估原问心阶难度，不能只引用旧注释中的模拟结论。

**D1｜扩展已有仙盟首领｜5–8 人日｜前后端协作**

**D2｜有条件上线论剑赛季｜6–10 人日｜后端主责**

- 前置：先核对实际守擂人数、有效对手数量、重复匹配比例及挑战分布。若经常只有少量同一对手，先改善匹配与反馈，赛季任务暂缓。

- 确定每对玩家计分频次、可计分挑战上限、结算时点、同分排序和异常挑战处理，避免原先“奖励次数用完后仍可无限计分”直接成为赛季冲榜捷径。
- 验收：从当前 1000 初始分体系迁入有清晰规则；结算只执行一次、可追溯；赛季边界的旧战斗归属固定。不默认给排名游戏币。

**D3｜形成小批量内容发布流程｜4–6 人日｜策划与开发共同负责**

- 建立每批内容的清单：稳定 ID、解锁条件、敌人/规则变化、奖励预算、美术、翻译、旧档影响和验证样本。
- 建议每两周一批小改进、每月复盘数值；具体频率服从制作能力。稳定后再加限时内容，不同时维护大量活动货币。
- 开关和时间表由服务器裁定。当前已有问道总开关和大比开关；周挑战、支线、赛季若需独立关闭，要明确新增能力，不能假设现在已经存在。
- 验收：一批内容关闭后，进行中的状态和已取得奖励仍可正确处理；重启、换节点和服务器日期变化不导致活动重复开启或多发奖励。

**D4｜只读诊断与运营观察｜4–6 人日｜后端主责，前端接管理页**

- 复用已有管理端，补问道版本分布、存档字节分布、结算错误、重复请求、关键瓶颈和资源流转的只读诊断。
- 诊断展示必要字段和错误定位标识，不公开完整私人存档、登录信息或无关账号数据。

- 验收：管理员能判断一次失败是配置、版本、状态冲突、资源不足还是系统错误；普通玩家不能读取其他人的诊断信息。

## 7. 数值与内容制作的统一标准

### 7.1 数值报告必须回答的问题

每次调参至少回答：谁会受影响、在哪个阶段、需要投入什么、获得什么，以及旧角色会发生什么变化。报告用同一批输入比较调前/调后，不把机器人胜率等同于真实玩家胜率。

| 维度 | 要观察的结果 | 调整原则 |
| --- | --- | --- |
| 首轮体验 | 首场战斗、第一次经营、第一次理解成长的用时与误操作 | 先减少解释和入口障碍，再考虑加速成长 |
| 三流派 | 同阶段首领/问心阶通过情况、可行牌组、依赖特定稀有牌程度 | 每派有不同玩法，不能要求某一派先攒满养成才可推进 |
| 资源收支 | 灵石/草/铁/声望与灵药的主要来源、消耗、等待 | 新消耗要说明来源，资源短缺应给可选择路径 |
| 洞府与祭炼 | 单位投入对应的真实属性、受上限截断部分 | 边际收益可解释，不叠出失去决策的无限数值 |
| 丹药与灵兽 | 不同火候、药力、灵兽的成本与通关收益 | 保留有效选择，不让一个选项在所有阶段都更优 |
| 付费道具影响 | 购买前后进度与游戏币玩法成绩差异 | 调整需单独评估，不形成未经预算的循环发币 |
| 社交转移 | 指名赠送、串门、仙盟对新老号资源的影响 | 尊重现有互助能力，同时观察刷取和集中转移 |

新数值必须有业务上限和输入边界，尤其是数量、价格、经验、倍率、概率、持续时间及批量操作次数。玩家可控数量先校验再计算；涉及钱包和游戏币继续复用项目安全算术与账本路径。

### 7.2 新增一批内容的最低交付清单

1. 一页玩法/剧情说明：目标玩家、解锁条件、入口、完成条件和重复规则。
2. 一张数据清单：稳定标识、依赖节点、敌人、数值、奖励、时间与资源上限。
3. 一张表现清单：文本、说话人、地图坐标、SVG/复用素材、音效、移动端和无动画状态。
4. 一组验证样本：新号、对应境界号、毕业号、旧号、跨日/周、重复请求、网络恢复。
5. 一份发布说明：开关、版本、存档影响、进行中对局策略、观察点和失败后的处理办法。

术语沿用现有设定：万宝阁是玩家间交易所，坊市是秘境里的商店；灵珠是秘境局内货币，灵石是宗门资源，道韵是秘境成长，游戏币是站点资产。

## 8. 存档、接口和并发的实现要求

### 8.1 存档与升级

- 读取缺失字段、有效旧值、非法值和未来版本要分别处理。`normalize` 补空表不等于完成版本迁移，也不等于校验全部边界。
- 对每次迁移保留原始样本，使用项目 `common` JSON 包做序列化；不要在业务代码中另接一套编解码器。
- 保存内容尽量是稳定 ID、实例、进度和时间，不把所有静态说明、完整历史回放和可推导展示字段反复复制到长期存档。
- 不改变现有玩家的 `wendao` 存档键。若未来拆表，只迁移确有独立查询或容量需求的部分，明确双写、切换和失败恢复顺序。
- 历练、宗门操作与秘境奖励都会影响同一份存档。做局部保存时不能用旧快照覆盖其他板块刚提交的资源或进度。

### 8.2 时间与幂等

- 使用服务器时间及现有游戏中心日期口径。当前日切按服务器本地日期，前端时区不能决定每日奖励归属；多实例部署要使用一致配置。
- 日切与周切采用显式标识，客户端显示截止时间。功课生成、开箱连续天数、丹药冷却、炼丹、孵化和跨周战斗要覆盖临界点。
- 可重复执行的迁移、结算、奖励、过期取回和批量操作都要定义重复请求结果。已完成动作不因重试获得第二份奖励。
- 进行中战斗使用开局快照，不因玩家在其他页面换装备或版本切换而临时改变本场属性。无法继续的旧局先设计一次性的结束与未用资产处理规则。

### 8.3 数据库与锁

- 新增业务写入使用 GORM 与现有事务辅助函数；MySQL/PostgreSQL 行锁使用 `lockForUpdate`，SQLite 由现有兼容策略处理。
- 保持既有挂单→按编号锁双人存档的锁顺序。跨仙盟、积分、奖励的新事务也应先写清锁对象和顺序，再实现并发行为。
- 发生余额不足、版本冲突、对象过期或权限不符时，货物、材料、积分与奖励一起保持一致；不能依赖异步补写完成一次核心成交。
- 三库均验证关键唯一约束、数值范围和升级行为。SQLite 单进程通过不能替代 MySQL/PostgreSQL 的并发验证。

这些结果提供接手基线，不能证明所有未来功能、三库升级、浏览器交互或线上数值已经验收。本次为文档交付，未执行全量前端构建、七语言人工检查、线上操作或本机临时升级脚本。

### 9.2 后续每批变更的必要验证

| 改动类型 | 最低验证 |
| --- | --- |
| 规则/数值 | 对应规则测试、固定案例调前/调后、受影响模式的收益边界 |
| 存档/迁移 | 旧样本升级、重复升级、未知版本、读写往返、容量、进行中状态 |
| 交易/领取/商店 | 失败回滚、重复提交、响应丢失、同一对象并发、三库关键行为 |
| 日期/周挑战/赛季 | 前一秒/边界/后一秒、跨期旧局、换节点、重复领奖 |
| 前端交互 | 关键流程行为验证、窄屏/暗色/键盘/减少动画、弱网与迟到响应 |
| 新内容 | A4 一致性检查、剧情条件、资源可达、老号可进入、i18n |

新增或重写的 Go 测试按项目要求使用 `require` 完成初始化与致命断言、`assert` 检查结果。测试保护实际资产、状态和接口契约；统计模拟单独做报告，不用大量随机循环或只有日志的“测试”代替断言。

前端发生代码改动后，在 `web/classic/` 使用 Bun 执行相关格式/ESLint、生产构建和适用的 i18n 检查。测试和 lint 的具体命令取当前 `package.json`；当前没有问道专属的前端测试脚本，若新增行为测试需一并交付运行入口。已有无关检查失败应独立记录，不把它伪称为本次变更引起，也不隐瞒受影响检查未通过。

### 9.3 一次内容或版本上线的顺序

1. 在可丢弃环境固定代码版本、规则版本、脱敏配置和旧档样本；先通过相关自动验证。
2. 演练数据库升级与第二次启动；同时验证进行中的主角、秘境和大比状态。
3. 发布兼容读取能力，再开放新内容写入。若使用灰度，服务器要能稳定识别试用范围，不能只在前端隐藏按钮。
4. 观察存档错误、状态冲突、扣发重复、字节增长、按模式游戏币净发放及关键流程完成情况。
5. 指标与实际错误稳定后扩大范围，并归档本次验证报告和配置版本。

停止条件：发现资产重复/丢失、未来版本被旧程序覆盖、合法存档无法保存、游戏币净发放明显偏离批准预算，或新内容导致旧流程无法继续。先关闭对应新内容写入口并保留现场，核对受影响对象，再制定恢复方案。

当前 `wendao` 开关管整个问道，大比另有开关；不要为了暂停秘境发币就误关整个养成入口。在允许继续游玩的场景，可经运营授权将相应 `SkillRule.DailyRewards` 设为 0，暂停后续发奖；领奖资格、进行中局和待发奖励如何恢复要先验收。恢复后的预算和资格不能靠猜测补发。

### 9.4 回退要区分代码、内容和数据

- 内容回退优先停用新增内容，保留已经获得的进度、资产及原始记录。
- 代码回退只允许回到能理解当前 schema 的版本。老二进制即使能忽略新字段读出来，也可能在下一次保存时把新字段丢掉。
- 一次数据库备份不是充分的资产恢复方案。直接恢复旧库会撤销之后的交易、领奖和站点其他业务；必须先界定一致性范围和后续流水，再由负责人批准执行。
- 同一玩家的问道资产已经通过万宝阁、仙盟和游戏币流水关联其他对象时，不得只回写一份旧 JSON 就宣称恢复完成。
- 迁移不支持安全降级时，采用兼容修复版本向前修复，记录影响范围，不试图自动猜测丢失的新字段。

## 10. 需要收集的数据和迭代规则

当前已确认管理端有按游戏奖励汇总；下表中的完整问道漏斗和资源观察尚需补建。先采集两至四周形成自己的基线，再设运营目标，不编造当前留存或通关数据。

| 指标 | 建议口径 | 用来决定什么 |
| --- | --- | --- |
| 新手漏斗 | 进入问道→创建→首场胜利→首次经营→首章首领；明确同一账号去重 | 优先改引导、难度还是入口 |
| 回流与活跃 | 问道内有效行为日活/周活；新建角色次日/七日回访 | 判断持续内容是否有效，避免混用全站活跃 |
| 成长瓶颈 | 按境界的等待时间、失败次数、缺失机缘和资源缺口 | 调整某段成长或补可选路线 |
| 构筑与平衡 | 按流派、养成档位、牌组与敌人的结果分布 | 是否存在单一强势解或不可达关卡 |
| 日常负担 | 一次返回的点击数、切页数、调火错过率、功课完成/换课 | 决定批量操作和任务调整 |
| 终局参与 | 问心阶分布、周挑战开始/完成、重复尝试 | 决定继续补终局还是开放新境界 |
| 社交供给 | 有效守擂人数、可选对手、重复匹配、仙盟参与 | 决定是否立项赛季和更多协作 |
| 经济与稳定性 | 各来源产出/消耗、挂单成交、游戏币净发放、错误与存档字节分布 | 确定预算、异常排查和容量扩展 |

埋点以服务器确认的业务结果为准，至少带模式、规则/内容版本、动作或结果和可关联的事件标识；同一业务结果不能因前端重渲染重复计数。只保留分析所需字段，不把完整存档、牌局隐私或登录凭据塞进分析日志。关键发奖和扣费仍以事务内业务记录为准，异步埋点不能成为记账依据。

每两周复盘一次：先看错误和资产一致性，再看玩家瓶颈和内容参与，最后选下一批任务。改动前写下预期变化和受影响人群，改动后比较同口径数据；玩家过少时辅以具体体验记录，不据很小样本宣称胜率、留存或付费改善。

## 12. 委派与完成标准

给接手者的简短说明可直接复制如下：

> 从 `dcaf1997dc8e142066c69c686e0bd0bc6d217e9d` 基线接手问道，先读 `pkg/wendao/world.md`、`story.md` 和本文。先执行 A1–A5，保留旧存档、进行中战斗与现有发币边界；之后按 B、C、D 顺序交付。每个任务提交代码、相关验证结果、配置/存档影响和简短使用说明。新玩法先做非游戏币奖励；不要重复开发已有洞府、灵兽、仙盟、万宝阁等基础系统。第六境界待 E1 评审后才实现。

每个工作包完成时至少交付：

- 与任务范围一致的实现或文档，以及可定位的提交/PR；不夹带无关重构和配置改动。
- 实际运行的验证命令、结果和未覆盖项；需要手工验收时提供步骤和观察结果。
- 新旧数据的变化、失败后的状态、进行中对局与重复请求处理。
- 用户可见文案、翻译/素材清单和使用说明；玩法或设定变化同步 `world.md`、`story.md`。
- 已知问题、下一步依赖和明确负责人；未完成的内容不能用“后续再补”算作已通过验收。

若需要压缩范围，优先延期：更多灵兽外观、复杂实时联机、仙盟大战、多活动货币、大规模剧情分叉和高境界扩展。优先保留：工具、存档、奖励、恢复、目标说明和有依据的平衡。
