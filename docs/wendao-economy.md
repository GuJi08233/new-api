## 发币流程与拒奖原因

九幽秘境按逐房种子/开局重放核对的胜负推进，大比按服务端状态推进。结算顺序是成绩取最高奖励档→账号/IP领取次数→共享总上限→累计有效时长。达标但时长不够时先取得待发权益并占一次领奖次数，随后当天有效结算补足时长可继续发；脚本判定局不累计有效时长，也不在该局发旧待发余额。

| `limited_by` | 实际含义 | 排查入口 |
| --- | --- | --- |
| `speed` | 服务端认定脚本/速度异常，不发奖 | 对局记录、风控告警；秘境逐房过快/回放不合法通常在结算前直接拒绝 |
| `time` | 已取得奖励但累计有效时长不足 | 当前游戏 `progress.seconds_today`、`pending_reward` 与每币所需秒数 |
| `daily` | 账号新领奖次数用完，包含配置为0 | 当前配置 `daily_rewards` 与 `progress.rewards` |
| `ip` | 同 IP 新领奖次数用完 | `progress.ip_rewards` 与归并后的来源 IP |
| `total` | 技巧/人机共享每日总额不足 | `free_daily_limit`、账号及 IP 的 `free_earned` |
| 空字符串 | 本次没有少发原因 | 未达成绩档时也可能是空；应连同score、reward、pending读取 |

旧版本请求、错误 token、重复请求内容不一致、回放非法、会话过期或另局取代会在结算前返回具体错误，不应把这些情况统计成正常零奖励。

**`DailyRewards=0` 的准确边界**：它停止新增领奖资格，玩法、资源和道韵仍照常。若账号当天已有 `PendingReward`，后续有效结算把时长补足时，仍会发放此前取得的待发权益。因此此字段不是“立即冻结全部游戏币支出”的开关。恢复为正数也不会对已完成场次重新计算奖励；重发原结算只返回原场次的score、reward和limited_by，余额、当日进度及当前规则则取最新值。

如果运营目标是冻结已经取得的待发权益，必须另行明确范围和恢复办法；本轮没有实现或启用这种能力。`wendao.enabled=false` 会影响整个问道，不能把它当成只停秘境发币而保留养成入口的开关。

## 公平性与数值结论的范围

九幽秘境不带主角境界、功法收藏、洞府、祭炼、灵兽和个人法宝法术配置；保留秘境自身道韵天赋与现有商店道具。宗门大比保留真实弟子、主殿、配队及库存回春丹，对手用 `平均弟子战力^0.75 × 主殿战力^0.25` 生成基准，并非完全等属性。

S4 的 `scripts/wendao-balance` 给了历练、问心阶、周天试炼的固定种子机器人样本，不是发币模式的真人胜率或经济预算证明。本轮接口测试只验证结算边界；没有据此宣称不同天赋/道具/成长组合的领奖概率相等，也没有测出线上留存、资源净流入或每币实际耗时。第三重独立敌人、重大成长/道具调整需要在相同输入下另做难度、有效耗时和奖励对照，不能混入本次发布收口。

## 管理端观察与诊断

复用现有 root 游戏管理，无新增钱包或账本：

- `GET /api/game/admin/setting`：核对启用状态、两种模式的档位/领奖次数/每币时长，以及共享上限和商店比例。存档 schema、会话格式版本与数据库行版本分别记录。
- `GET /api/game/admin/overview` 的 `game_rewards`：来自 `SumGameRewardsByGame` 的当日实发净额。九幽秘境键为 `wendao`，大比为 `wendao_tournament`。它没有完整的资源产消或待发权益看板，不能只看实发为0就认定没有待发负债。
- `GameSession`：按用户、游戏、session ID 定位score、reward、limited_by及结算明细。详情中的秘境loot/crystals、大比stone/rep/pills提供当次资源证据；长期存档、时间和请求收据用于判断是否已入账。
- 游戏币变动写 `GameCoinLog`，正奖励为 `game_reward`，引用场次ID；用户 `GET /api/game/logs` 能查自己的流水。奖励还会记请求来源的系统审计日志，脚本判定另记风控告警。完整私人存档不应作为普通用户诊断接口公开。

一次结算提交失败返回503时应保留场次并用同一请求重试。数据库版本冲突先读最新状态；已完成场次不靠“补发一次”修复响应丢失。新来源收益或重复记账需要按场次、日志和存档一起核对。
